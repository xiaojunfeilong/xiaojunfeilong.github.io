ERP 与 OA 集成：我反复踩过的坑，以及一套可复用的方法论

不要从「把两边数据全同步」起手。先定主数据权属、单据幂等和对账口，集成才不会在上线第三周炸开。

集成项目失败，很少是因为接口文档写得不够长。更常见的是：两边都觉得「对方以我为准」，上线后同一张采购单在 OA 里通过了、在 ERP 里却生成了两次，或者状态永远停在「处理中」。

下面是我反复踩过、后来写成检查单的东西。

坑一：先同步字段，后讨论权属

「物料编码、供应商、部门，两边都有，对一下就好。」对完才发现：OA 里的部门是行政编制，ERP 里的部门是成本中心；供应商在一边能停用，另一边只做标记。

先写权属表。 每个主数据只有一个写入源。另一边只读，或只允许在自己的扩展字段里写。权属不写清，后面所有映射都是猜测。

坑二：用「最新一条」当真相

审批流会退回、会加签、会在网关里超时重试。如果你按「最后一次回调」覆盖 ERP 单据，退回再通过就可能改掉不该改的数量。

正确的做法是给每一次入站事件一个 业务键：审批实例ID + 节点 + 动作 + 幂等号。同样的键只处理一次。重试必须安全。

idempotency_key = oa_request_id + ":" + node_id + ":" + action
if already_processed(idempotency_key):
    return stored_result
create_or_update_erp_bill(...)
store(idempotency_key, result)

坑三：把审批状态当成业务状态

OA 的「已归档」不等于 ERP 的「已入库」。人关心的是货物和账，不是流程节点名称。映射时要显式维护一张状态机，禁止「有新状态再临时加 if」。

建议最小集合：草稿 / 待审 / 已通过待执行 / 已执行 / 已关闭 / 已作废。OA 节点只向这六个状态投影。

坑四：没有对账，只有日志

接口日志能证明「我发出去了」，不能证明「两边还一致」。对账要成为功能，而不是出了事故才写的 SQL。

每日最少三张表：

  • 今日应建未建
  • 今日数量不一致
  • 今日状态不一致

发给固定的人，而不是丢进无人看的群。

五步拆法（可直接拿去开工会）

  1. 圈定一个闭环：例如「请购审批通过 → ERP 采购申请」。不谈主数据大一统。
  2. 画对象，不画系统：请购单、采购申请、物料、供应商，各自的主键和生命周期。
  3. 写权属与映射：谁写、谁读、冲突时以谁为准、空值怎么处理。
  4. 定幂等与失败策略：超时重试、人工补偿、禁止静默丢消息。
  5. 先对账再放量：灰度 10 张单，对平了再放开部门。

集成的目标不是把两个系统焊死，而是让现场少录一遍、少对一次账。接口数量可以很少，闭环必须完整。
